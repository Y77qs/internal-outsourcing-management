## 1. Executive Summary

本项目将建设一套面向企业内部测试外包人员的后台管理系统，为测试外包人员、上级领导和管理员提供用户注册登录、权限管理、上岗申请、审批流转、工作日志、绩效评定和操作审计能力，用于解决外包人员管理流程人工化、审批过程不透明、数据分散、权限边界不清和操作难追踪的问题。项目交付后，预期能够完成外包人员管理核心流程线上化，并作为后端开发 PTA 实战项目，覆盖 Spring Boot、MyBatis-Plus、MySQL、Redis、JWT/RBAC、Swagger、JMeter、Checkstyle 等企业后端常见技术栈。

🔶 **Assumption**：本 PRD 基于 mentor 任务需求文档整理，业务场景为模拟企业内部管理流程，不代表已经经过真实企业用户访谈或生产环境验证。

## 2. Problem Statement

### Who Has This Problem?

主要受影响用户包括：

- 企业内部负责管理测试外包人员的管理员。
- 需要审批外包人员上岗申请和绩效情况的上级领导。
- 需要提交上岗申请、工作日志并查看审批结果的测试外包人员。

### What Is the Problem?

在测试外包人员管理场景中，如果上岗申请、审批、日志、绩效和权限分配依赖线下沟通或分散表格，会出现以下问题：

- 外包人员上岗申请缺少统一入口，申请状态难以实时查看。
- 上级领导审批缺少结构化流程，审批意见、审批时间和审批结果容易分散。
- 管理员对用户、角色、权限、绩效和日志的管理不够集中。
- 关键业务操作缺少统一日志，后续审计和问题排查成本较高。
- 外包人员绩效信息缺少标准化记录，A/B/C 等级管理容易受人工记录影响。


### Why Is It Painful?

- **用户影响**：测试外包人员无法清楚知道申请是否已提交、是否被审批、为什么被驳回；上级领导需要在分散信息中寻找待审批事项；管理员难以快速追踪人员、权限和绩效变化。
- **业务影响**：审批和管理链路不透明会降低管理效率，增加沟通成本，关键操作缺少留痕会影响后续审计和问题定位。

### Evidence

- **任务材料**：要求系统需要覆盖用户管理、上岗申请、日志提交、绩效评定等核心功能。
- **技术要求**：明确要求使用 Spring Boot 3.x、MyBatis-Plus、MySQL、Redis、Swagger、Postman、JMeter、Checkstyle、日志框架等技术。
- **交付要求**：明确要求交付源代码、架构文档、UML 类图、接口文档、数据库 ER 图、SQL 脚本、索引优化说明、测试文档和问题 list。

## 3. Target Users & Personas

### Primary Persona：测试外包人员

- **角色**：参与企业测试项目的外包测试人员。
- **目标**：完成账号注册登录，提交上岗申请，查看审批结果，提交工作日志，查看个人绩效。
- **痛点**：不知道申请处理进度；日志和绩效记录分散；被驳回时缺少清晰原因。
- **当前行为**：🔶 **Assumption**：可能通过人工沟通、表格或聊天工具提交申请和日志。
- **Jobs-to-Be-Done**：当我需要进入项目开展测试工作时，我希望在线提交上岗申请并及时看到审批结果，以便减少反复沟通。

### Secondary Persona：上级领导

- **角色**：负责审核测试外包人员上岗申请、查看日志和参与绩效评定的审批人员。
- **目标**：快速查看待审批申请，批量或分页处理申请，记录审批意见，查看人员日志和绩效。
- **痛点**：待审批事项分散；审批记录不统一；无法快速追踪某个人员的历史申请和工作表现。
- **当前行为**：🔶 **Assumption**：可能通过线下确认、聊天记录或表格完成审批。
- **Jobs-to-Be-Done**：当我需要管理外包人员上岗时，我希望集中查看申请并完成审批，以便保证流程可追踪、结果可复盘。

### Secondary Persona：系统管理员

- **角色**：负责系统配置、账号管理、权限维护、日志查看和绩效数据维护的管理人员。
- **目标**：统一管理用户、角色、权限、操作日志和绩效记录。
- **痛点**：权限边界不清容易带来安全风险；缺少日志会导致异常操作难以追踪；数据表结构不规范会影响后续扩展。
- **当前行为**：🔶 **Assumption**：可能依赖人工维护账号和权限，或使用多个分散工具管理。
- **Jobs-to-Be-Done**：当系统用户和业务数据增加时，我希望通过角色权限和日志审计保持系统可控，以便降低管理和排查成本。


## 4. Strategic Context

### Business Goals

- **管理目标**：将测试外包人员上岗申请、审批、日志、绩效和权限管理集中到同一后台系统中。
- **效率目标**：通过线上审批和状态流转减少人工沟通成本。
- **审计目标**：通过操作日志记录关键动作，支持后续问题追踪。
- **学习目标**：通过真实业务风格项目覆盖后端实习所需的主流技术栈和交付物。



### Competitive Landscape

- **当前替代方案**：表格、聊天工具、线下审批、通用 OA 系统或简单后台 CRUD 系统。
- **本项目差异点**：结合测试外包人员管理场景，将权限、申请、审批、日志、绩效和工程化交付集中到一个后端项目中。
- **工程亮点**：项目覆盖 Java 框架、缓存、MQ、数据库、架构分层、异步任务、日志监控、性能优化、SQL 优化和 JVM 监控等方向。


### Why Now?

该项目现在需要启动，是因为第一周任务重点是需求分析与技术选型，后续第二周会进入 Spring Boot 框架搭建、MySQL/Redis 配置、登录鉴权和 RBAC 权限控制等编码阶段。如果第一周没有明确 PRD、系统边界和验收标准，后续数据库设计、接口设计和代码实现容易出现范围漂移。

## 5. Solution Overview

### Solution Description

建设一个基于 Spring Boot 3.x 的内部测试外包人员管理后台。系统采用 Controller、Service、Mapper 分层结构，使用 MyBatis-Plus 操作 MySQL 数据库，使用 Redis 支撑登录状态、热点数据或业务锁，使用 JWT + RBAC 实现认证授权，使用 Swagger/Knife4j 输出接口文档，并通过 Postman、JMeter、Checkstyle 等工具完成联调、压测和代码规范检查。

系统核心业务围绕三类角色展开：测试外包人员提交上岗申请和工作日志；上级领导查看并审批申请、查看日志和绩效；管理员管理用户、角色、权限、绩效和操作日志。系统需要支持关键操作留痕，后续可扩展 MQ 异步通知、Elasticsearch 日志检索、Prometheus/Grafana 监控和 Docker 容器化部署。

### Key Features

| 模块 | 核心能力 |
| --- | --- |
| 用户与认证 | 注册、登录、退出、JWT Token、用户启用禁用 |
| 权限管理 | RBAC 权限控制、角色分配、权限分配 |
| 上岗申请 | 提交申请、查看详情、撤回待审批申请、状态流转 |
| 领导审批 | 分页查询待审批申请、审批通过、驳回、记录审批意见 |
| 工作日志 | 提交日志、修改个人日志、按人员/项目/日期查询日志 |
| 绩效管理 | A/B/C 绩效评定、修改原因、绩效历史 |
| 操作日志 | 记录操作人、模块、类型、接口、参数、结果、时间 |
| 接口文档 | Swagger/Knife4j 生成 API 文档，统一 `ResultVO` 响应 |
| 测试与压测 | JUnit/Mockito 单测、Postman 联调、JMeter 压测 |
| 工程规范 | Maven 构建、Checkstyle 规范、日志统一配置 |

### User Flows

**上岗申请审批流程**

1. 测试外包人员注册并登录系统。
2. 测试外包人员填写并提交上岗申请。
3. 系统校验申请参数，并将申请状态置为“待审批”。
4. 上级领导分页查看待审批申请。
5. 上级领导选择通过或驳回，并填写审批意见。
6. 系统保存审批结果，记录审批日志。
7. 测试外包人员查看审批状态和审批意见。

**绩效管理流程**

1. 管理员或上级领导查询外包人员。
2. 选择人员和绩效周期。
3. 设置绩效等级 A/B/C 并填写说明。
4. 系统保存绩效记录。
5. 如果发生修改，系统记录修改原因和操作日志。
6. 🔶 **Assumption**：使用 Redis 分布式锁防止多人同时修改同一人员同一周期绩效。

### Guardrail Metrics

- 不为了堆叠技术栈而牺牲核心业务闭环；若时间不足，优先保证用户、权限、申请、审批、日志、绩效主链路完整。
- 不虚构真实业务增长数据；业务效率、审批耗时等真实指标若无数据支撑，必须保留为假设或待确认。
- 不引入与当前学习目标无关的复杂前端、移动端或生产级高可用能力，避免范围失控。


## 7. User Stories & Requirements

### Epic Hypothesis

我们相信，为企业测试外包人员建设一套包含用户权限、上岗申请、领导审批、工作日志、绩效评定和操作审计的后台管理系统，可以完成外包人员管理核心流程线上化，并帮助实习生覆盖后端开发主流工程能力。项目成功将通过核心业务闭环完成度、文档交付完整度、接口测试结果、单元测试覆盖率和压测结果进行衡量。

### Story 1：用户注册与登录

As a 测试外包人员, I want 注册并登录系统, so that 我可以提交上岗申请、日志并查看个人审批和绩效信息。

**Acceptance Criteria:**

- [ ] 用户可以使用用户名、密码、手机号或邮箱等必要信息注册账号。
- [ ] 系统校验用户名不可重复。
- [ ] 密码必须加密存储，不允许明文保存。
- [ ] 注册成功后默认分配测试外包人员角色。
- [ ] 用户登录成功后返回 JWT Token。
- [ ] 被禁用用户不允许登录。
- [ ] 登录、退出等关键操作需要记录操作日志。

### Story 2：RBAC 权限控制

As a 管理员, I want 管理用户、角色和权限, so that 不同角色只能访问其授权范围内的功能。

**Acceptance Criteria:**

- [ ] 系统至少内置管理员、上级领导、测试外包人员三类角色。
- [ ] 管理员可以查询用户列表、查看用户详情、启用或禁用用户。
- [ ] 管理员可以为用户分配角色。
- [ ] 管理员可以查询角色和权限列表。
- [ ] 系统基于 JWT + RBAC 判断接口访问权限。
- [ ] 测试外包人员不能访问管理员专属接口。
- [ ] 未登录或 Token 无效时，接口返回统一错误响应。

### Story 3：提交上岗申请

As a 测试外包人员, I want 在线提交上岗申请, so that 我的上岗流程可以被上级领导审批并留痕。

**Acceptance Criteria:**

- [ ] 用户登录后可以填写所属部门、项目名称、岗位类型、申请原因等信息。
- [ ] 提交成功后申请状态为“待审批”。
- [ ] 同一用户同一项目不允许重复提交待审批申请。
- [ ] 用户可以查询个人申请列表和申请详情。
- [ ] 用户可以撤回仍处于待审批状态的申请。
- [ ] 申请创建、撤回等操作需要记录操作日志。

### Story 4：领导审批上岗申请

As an 上级领导, I want 分页查看并审批上岗申请, so that 我可以高效处理外包人员上岗流程。

**Acceptance Criteria:**

- [ ] 上级领导可以分页查询待审批申请。
- [ ] 上级领导可以查看申请详情。
- [ ] 上级领导可以审批通过申请。
- [ ] 上级领导可以驳回申请并填写审批意见。
- [ ] 只有待审批状态的申请可以被审批。
- [ ] 已通过或已驳回的申请不允许重复审批。
- [ ] 系统记录审批人、审批意见、审批结果和审批时间。
- [ ] 🔶 **Assumption**：审批通知可通过 MQ 异步处理，是否必须实现待确认。

### Story 5：提交与查询工作日志

As a 测试外包人员, I want 提交工作日志, so that 我的工作内容、完成情况和问题风险可以被记录和查询。

**Acceptance Criteria:**

- [ ] 测试外包人员可以新增工作日志。
- [ ] 工作日志至少包含项目名称、工作日期、工作内容、问题记录、完成情况和提交时间。
- [ ] 测试外包人员可以修改自己的日志。
- [ ] 测试外包人员只能查看和修改自己的日志。
- [ ] 上级领导或管理员可以按人员、项目、日期查询日志。
- [ ] 日志提交和修改操作需要写入操作日志。

### Story 6：绩效评定与历史查询

As a 管理员或上级领导, I want 维护测试外包人员绩效等级, so that 企业可以按 A/B/C 等级管理外包人员表现。

**Acceptance Criteria:**

- [ ] 管理员或上级领导可以查询绩效列表。
- [ ] 管理员或上级领导可以查看绩效详情。
- [ ] 管理员或上级领导可以新增绩效记录。
- [ ] 绩效等级只能为 A、B、C。
- [ ] 修改绩效时必须填写修改原因。
- [ ] 系统保留绩效历史记录。
- [ ] 同一人员同一周期只能有一条当前有效绩效记录。
- [ ] 修改绩效需要记录操作日志。
- [ ] 🔵 **Open Question**：绩效周期按月、季度还是项目周期统计，需要 mentor 确认。

### Story 7：操作日志与审计

As a 管理员, I want 查询系统关键操作日志, so that 我可以审计用户行为并定位问题。

**Acceptance Criteria:**

- [ ] 系统自动记录用户管理、上岗申请、审批、工作日志、绩效管理等关键操作。
- [ ] 操作日志至少包含操作人、操作模块、操作类型、请求接口、关键参数、操作结果和操作时间。
- [ ] 操作失败时记录错误信息。
- [ ] 管理员可以按用户、模块、时间范围筛选日志。
- [ ] 日志中不输出明文密码、Token 等敏感信息。
- [ ] 🔶 **Assumption**：高级阶段可将日志写入 Elasticsearch 并支持检索。

### Story 8：接口文档、测试和交付

As a mentor / 项目评审, I want 看到完整接口文档、测试结果和交付材料, so that 我可以判断项目是否达到 PTA 要求。

**Acceptance Criteria:**

- [ ] Swagger/Knife4j 可以访问并展示核心接口。
- [ ] 接口文档包含路径、请求方式、请求参数、响应字段和错误码说明。
- [ ] 接口统一返回 `ResultVO`。
- [ ] Postman 覆盖核心接口联调记录。
- [ ] JUnit + Mockito 覆盖核心 Service 或工具类逻辑。
- [ ] JMeter 覆盖多人登录、提交申请、审批等压测场景。
- [ ] 最终交付源代码、架构文档、UML 类图、ER 图、SQL 脚本、索引说明、部署手册、测试文档和问题 list。

### Constraints & Edge Cases

- 接口必须进行参数校验，非法参数返回统一错误响应。
- 列表查询必须分页，避免一次性返回大量数据。
- 删除或禁用用户时，需要考虑其历史申请、日志、审批和绩效数据是否保留。
- 绩效并发修改需要考虑数据覆盖问题。
- 操作日志需要避免记录敏感信息。
- 若高级技术栈来不及实现，应保证基础业务链路先完成。

## 8. Out of Scope

### Not Included in This Release

- **真实企业 OA/人事系统集成**：当前项目聚焦 PTA 实战，不接入真实企业系统。
- **复杂多级审批流引擎**：第一阶段按单级领导审批设计，避免流程引擎复杂度过高。
- **移动端 App**：当前默认后台 Web 或接口项目，不开发独立 iOS/Android 应用。
- **复杂 BI 报表**：绩效统计只做基础等级和历史记录，不做高级可视化分析。
- **生产级高可用部署**：Docker 和监控作为扩展实践，不要求达到真实生产多节点容灾标准。
- **完整微服务拆分**：Spring Cloud Alibaba 作为高级扩展方向，第一阶段不强制拆分为多个微服务。
- **真实短信/邮件/企业微信通知**：审批通知可先使用 MQ 模拟异步处理，不强制接入真实通知渠道。

### Risks & Mitigations

| 风险 | 影响 | 缓解方式 |
| --- | --- | --- |
| 技术栈范围过大 | 可能导致核心业务没做完 | 先完成基础业务闭环，再做 MQ、ES、监控、Docker 等扩展 |
| 权限控制设计不清 | 可能出现接口越权 | 使用 RBAC 模型，提前定义角色权限矩阵 |
| 数据库设计不规范 | 后续功能扩展困难 | 第一周完成 ER 图，至少满足第三范式，关键字段建立索引 |
| 日志记录敏感信息 | 带来安全风险 | 日志统一脱敏，不记录明文密码和 Token |
| 高级组件本地环境配置困难 | 影响开发进度 | 将高级组件分为必做和选做，必要时使用 Docker 降低环境差异 |

### Coding & Delivery Requirements

- 源代码需符合阿里巴巴 Java 开发规范。
- 类名使用大驼峰，方法和变量使用小驼峰，常量使用全大写下划线。
- Controller 接口方法需要添加 JavaDoc 或 Swagger 注解。
- 复杂业务逻辑需要补充简洁注释。
- 日志统一使用 SLF4J 门面，底层可使用 Logback 或 Log4j2。
- 最终交付需要包含源代码、必要文档、ER 图、UML 类图、SQL 脚本、测试记录、部署手册和问题 list。
